## Phase 1 — Minimal event kernel (P0, required per Phase 0.1)

1. **Store**: SQLite at `~/.daemon/events.db`, table
  `events(id, run_id, seq, type, payload_json, created_at)` exactly per
  spec. `run_id` = session id; `seq` is per-run monotonic. Append-only:
  no UPDATE/DELETE code paths exist for this table.
2. **Types** (spec list, verbatim): run.started, message.user,
  message.assistant, plan.created, plan.approved, tool.called,
  tool.result, permission.decided, verification.result,
  checkpoint.created, run.finished. Appended from the runtime at the
  points where the journal/audit already fire — one new module
  (`daemon/events.py`), thin call sites, no behavior change.
3. **Projections**: messages (from message.* events), plan state (from
  plan.*), checkpoints (from checkpoint.created). The existing
  transcript.jsonl remains the crash-safe message journal; the kernel
  is the typed cross-cutting record. Replay compares the kernel's
  message projection against transcript.jsonl — divergence is a bug
  and is reported, per spec 1.2.
4. **`daemon replay <run_id>`**: reconstructs projected state, diffs
  against the live session store, prints the diff or "identical".
   Deterministic: two invocations produce byte-identical output.
5. **Acceptance** (spec 1.3): a run's full lifecycle is reconstructable
   from events alone; replay deterministic across two invocations;
   existing tests still pass (557 + new). Gate 1: tests green, replay
   deterministic, no schema migration drops data (the table is new;
   nothing migrates).

## Phase 2 — The six deliverables (one commit per item, spec order)

### 2.1 `daemon selftest` — the release gate as a command

Legs: doctor checks · demo run in a throwaway workspace (temp dir, git
init, trivial task) · offline eval (existing evals/, no network) ·
repomap on the throwaway workspace · memory add/read/invalidate
round-trip · worktree create/list/remove round-trip · sandbox probe
(2.6 backend available and fail-closed — actually executes a denied
command and asserts denial) · model leg (only if credentials present:
one minimal real completion).

Verdict rules (spec, verbatim intent): PASS only if every leg is PASS;
PARTIAL if any leg is SKIP; FAIL otherwise. Never print PASS on a SKIP.
Exit codes: 0 PASS, 1 PARTIAL, 2 FAIL. `--json` machine-readable.
Every leg has a timeout; no leg can hang the command. SKIP lines name
the leg and the reason (no credentials / no sandbox backend).

Acceptance (spec): a deliberately broken install (renamed module)
yields FAIL with the correct leg named; a credential-less machine
yields PARTIAL naming the skipped leg. Both proven by tests.
**Expected on this machine: PARTIAL (model leg SKIP — no credentials).**

### 2.2 Front door

Bare `daemon` opens the REPL (already true). With no credential, the
REPL offers the labeled demo up front ("No API key found. Run the
offline demo? [Y/n]") instead of AuthError. `daemon init` scaffolds
`.daemon/`, a starter `AGENTS.md`, and a commented config file, and
prints next steps. Hard rules: demo fully offline, never pretends to
be a real agent, never persisted as the user's provider; init
idempotent (second run = identical state). Acceptance: fresh venv, no
config → demo offered and completes; init twice → identical state;
with a key → REPL opens. All tested.

*Reconciliation:* the spec says init writes "a commented daemon.toml";
this codebase's config file is `config.toml` (`~/.daemon/config.toml`,
`<ws>/.daemon/config.toml`). Init writes the codebase's real file —
flagged at Gate 0.

### 2.3 Plan mode

`daemon run --plan "task"` (and REPL /plan): planner → render → STOP,
nothing executes. Plan is JSON: `{tasks: [{id, description, files,
verification, risk}], success_criteria: [...]}` (the existing planner's
Task shape maps onto this; the persisted form is this JSON). The user
can EDIT the plan (editor, schema re-validated) before approving.
Approval goes through the permission broker like a mutating action;
denied approval is a recorded event (plan.approved is joined by a
denied decision in permission.decided + audit). On approval, execution
proceeds task-by-task with per-task verification. Hard rules:
malformed plan → reject and re-prompt, never execute; plan persisted
to the event log (plan.created, plan.approved); per-task verification
failure → task marked failed, loop stops or asks, never silently
continues. Acceptance: a plan with a deliberately failing task stops
at that task with evidence; an edited plan is honored; denied approval
produces zero tool calls. All tested.

### 2.4 Environments

`daemon env create|use|reset|list|show`. An env bundles config,
permission policy, memory store, and Reflex state — a state bundle,
not a directory alias. `use` persists the active env and scopes
subsequent runs; runs record their env in the event log. Hard rules:
reset is deterministic — same env, same baseline, **byte-identical
state, verified by test**; memory and Reflex state are scoped per-env
and cannot leak across envs; an env's permission fragment is validated
against the classifier DENY floor like any config (an env cannot widen
past the floor or disable audit — carried over from the v0.9.0 sketch
and consistent with the spec's broker supremacy). Credentials and
sessions are never part of an env. Acceptance: create → use → run →
reset → run again yields the identical baseline; env A's state is
invisible in env B. Both tested.

*Design note for Gate 0:* baseline = the state captured at `create`
time (post-create snapshot). Reset restores that snapshot. Snapshot
storage lives under `~/.daemon/envs/<name>/` as files + a manifest
with content hashes — the hashes are what the byte-identical test
asserts.

### 2.5 Diffs at decision + `daemon undo`

Permission ASK for a file edit shows the actual unified diff,
truncated per a documented budget (default: 200 lines / ~8k tokens,
configurable) with a "… N more lines" marker; the diff is a preview —
computing it mutates nothing — and it is the same computation that the
applied edit reports afterwards. `daemon undo` reverts the last
checkpoint; `daemon undo --list` shows undoable checkpoints;
`daemon undo <checkpoint_id>` jumps to a specific one. Hard rules:
undo operates on checkpoint EVENTS (the kernel's checkpoint.created
projection is the index; the existing snapshots remain the byte
storage); undo of an undo is not a thing — documented in help and
docs. Acceptance: a large edit's prompt shows the truncated diff with
marker; undo restores the exact checkpointed bytes (test); --list
matches checkpoint events (test).

### 2.6 Sandbox — pluggable backend, container-first

`SandboxBackend` interface: `run(command, cwd, env, timeout,
network_policy) -> {exit_code, stdout, stderr, timed_out}`, plus
`available()` and `probe()`. Backends:

- **ContainerBackend** (spec default): Docker or Podman CLI, whichever
  is present (this host: Podman yes, Docker no). No network by default
  (egress allowlist), read-only root, workspace mounted rw, scrubbed
  env, no host secrets.
- **BwrapBackend**: the v0.5.0 bubblewrap implementation, re-homed
  behind the interface. *Reconciliation (Gate 0 decision):* the spec
  assumed no native backend existed and made Seatbelt/Landlock stubs;
  bwrap here is real, shipped, and five-review-passed, so it is kept
  as a full backend, not stubbed or deleted. Selection order:
  container when available → bwrap → none. Seatbelt/Landlock remain
  stubs per spec.
- No backend available: selftest sandbox leg = SKIP (no sandbox
  backend); `run` warns and proceeds under the permission engine,
  with commands classified dangerous still denied (fail-closed).

Hard rules (spec): unknown command → deny by default under sandbox;
sandbox unavailable → dangerous commands denied; no secret leakage
(env scrubbing stays the v0.5.0 segment-based stripper); the selftest
probe actually executes a denied command and asserts denial.
Acceptance: a network-egress command fails inside the container
backend; a secret env var is absent inside; the selftest sandbox leg
passes only when both hold.

## Risks

- **Phase 1 scope creep**: the kernel is an enabler. Mitigation: the
  type list and projections are closed sets from the spec; anything
  beyond them is out of scope for 0.9.0.
- **Container backend on this host**: Podman exists (VEIL runs in it);
  Docker does not. The backend must probe both and degrade honestly.
  Rootless podman networking quirks are the known unknown — the
  egress test is the arbiter.
- **Env determinism**: byte-identical reset fails if any bundled store
  embeds timestamps/random ids. The manifest-hash test will surface
  offenders; stores may need a canonicalization pass at snapshot time
  (documented in the env module, not hacked per-test).
- **Front door is adoption, not correctness** (user's guardrail): it
  is timeboxed — if §2.2 slips, 0.9.0 still ships without it.

## Explicitly out of scope

Per-task model routing in the main loop · hard Reflex signals ·
PyPI publishing (user's manual step) · native Seatbelt/Landlock
implementations (stubs only) · any change to the held v0.4.1 tag or
the v0.5.0 branch · pushing anything.
