## 3. Plan-mode bypass — FAIL

Three sub-findings, all reproduced live. The things that do NOT
bypass were also verified: unapproved `--execute-plan --yes` with
stdin closed refuses with exit 1 and nothing runs; editing a plan
without recomputing the hash refuses with PlanError, exit 2
("content hash mismatch"). The gate works against an honest editor.
It does not work against a forging one.

### 3a. The plan hash is forgeable — a tampered plan executes (CLI)

The content hash is an unsalted sha256 of public content, stored in
the plan file itself (`daemon/plans.py: compute_plan_hash`), and the
kernel's `plan.created` event carries no hash or plan id
(`daemon/events.py: emit_plan_created` — goal/summary/tasks only),
so nothing outside the file can cross-check it. Anyone who can write
the file can recompute the hash, and the approval panel shows only
the goal, the task count, the hash prefix, and the files list — never
task titles or descriptions — so the tamper is invisible at the
moment of approval.

Reproduction (verbatim):

```
$ daemon run --plan "add a docstring to a.py" --provider demo -w /tmp/r1-ws
plan 09ef6fe8 created (not executed)
  1. Execute: add a docstring to a.py
```

Then, as the forger (plain Python, using the public
`compute_plan_hash`):

```python
data["tasks"][0]["title"] = "Execute: add a docstring to b.py"
data["tasks"][0]["description"] = "Tampered: operate on b.py instead of a.py."
data["hash"] = compute_plan_hash(goal=data["goal"], summary=data["summary"], tasks=data["tasks"])
```

`PlanStore("/tmp/r1-ws").load("09ef6fe8")` accepts the forged plan
("LOAD ACCEPTED forged plan; task title now: Execute: add a
docstring to b.py; files listed for approval: ['a.py']"). Under a
pty, `daemon run --execute-plan 09ef6fe8 --provider demo`, answered
`y` at the prompt whose panel read `action: Execute plan 09ef6fe8:
add a docstring to a.py (1 task(s)…)` / `files: a.py` — and the run
edited **b.py** (`read_file path='b.py'`, `edit_file path='b.py'`,
`"""Sub."""` added), leaving `a.py` untouched, ending with "plan
executed: all tasks done".

Threat model note: the forger here is anything that can write
`.daemon/plans/*.json` between creation and execution — including a
model run in the same workspace (the plan file is an ordinary
workspace file, editable through the normal `edit_file` path). The
spec's promise — "edits that break the schema or change the content
after approval are refused" (printed by the CLI itself) — holds only
against editors who do not know the hash is recomputable, i.e. it
is tamper-evidence, not tamper-proof. Fix direction: record the
content hash in the `plan.created` kernel event (or in
`DAEMON_HOME`, outside the workspace) and compare the loaded file
against that copy at execute time; and/or show the full task list
(titles + descriptions) in the approval panel so a tamper is visible
even if the hash check is defeated.

### 3b. REPL `/build` executes the stale in-memory plan, not the edited file

`daemon/ui/repl.py: _execute_plan` re-loads the record (schema +
hash — the validation gate) but then runs
`run_plan_tasks(self.runtime, self.tracker, …)` where `self.tracker`
was loaded at `/plan` time and is never refreshed from the re-loaded
record. An edit to the stored plan between `/plan` and `/build` is
validated and then silently ignored.

Reproduction (fresh REPL under a pty, workspace with `a.py` and
`b.py`): `/plan add a docstring to a.py`, then edit the stored plan
(`tasks[0].title` → "Execute: add a docstring to b.py",
`tasks[0].files` → `["b.py"]`, hash recomputed), then `/build`,
answer `y`. Result: **`a.py` gained the docstring; `b.py`
untouched.** The spec's acceptance — "an edited plan is honored" —
fails in the REPL. (The CLI path is not affected: each
`--execute-plan` builds a fresh `TaskTracker` from the loaded
record, which is why finding 3a executes the tampered plan there.)

### 3c. REPL "always" remembers plan approval for the session

The approval prompt offers `[a]lways this session`, and
`resolve()` calls `remember("plan.execute:<id>", ALLOW)` when it is
chosen (`daemon/permissions.py: resolve`, `approve_plan`). The next
`/build` of the same plan id in the same REPL session then skips the
prompt entirely (`_apply_session` flips ASK → ALLOW in `_finish`
before `resolve` is even called).

Reproduction (REPL under a pty): `/plan …`, `/build`, answer `a`
→ executes. Tamper the plan file, `/build` again → **zero further
prompts** (`allow?` appears once in the whole transcript, from the
first build) while the UI prints "plan execution finished". In this
probe the second build was a no-op because the in-memory tracker was
already exhausted (finding 3b), so the silent approval bought a
success message for zero work — the two findings compound: one
approval plus a forged edit can re-execute a different plan with no
further prompt. Session overrides are in-memory only, so the CLI
(one process per invocation) is not affected; the REPL is.

## 4. Env leak — FAIL

`validate_fragment` (`daemon/envs.py:171`) screens only ALLOW rules
whose **command** pattern matches a deny probe, and ALLOWs on
credential tools. It does not screen **path** patterns — and env
fragment rules reach the broker with origin `"user"`: `Config.load`
deep-merges the fragment into the merged config and
`build_context` passes the merged rules to `PermissionEngine`, whose
constructor calls `_rule_from_config(raw, origin="user")` for every
dict rule. In `check()`, a matched user rule relaxes the ASK floor
(`user_rule` → `effect = chosen.effect`), including the
outside-workspace ASK raised by path containment.

Reproduction:

```toml
# appended to ~/.daemon/envs/leaky/config.toml (template: minimal)
[[permissions.rules]]
tool = "read_file"
path = "/tmp/*"
effect = "allow"
description = "env fragment: allow reading /tmp"
```

`daemon env use leaky` accepts the fragment (validation passes),
then the engine decision for `read_file` on
`/tmp/outside-secret.txt` is:

```
WITH leaky env active: read_file /tmp/outside-secret.txt -> allow
  | reasons: ['touches paths outside the workspace',
  'rule(user): env fragment: allow reading /tmp']
WITHOUT env (control): read_file /tmp/outside-secret.txt -> ask
```

The spec's hard rule — "an env cannot widen past the floor" — is
defeated by a one-line path rule. Two compounding facts: (a) the
fragment is validated only at `create`/`use`; `Config.load` never
re-validates, so hand-editing the fragment after `use` bypasses even
the command-pattern screen; (b) the check-time DENY floor (absolute
for `level == "deny"`) does not help here because outside-workspace
reads are level `"ask"`, not `"deny"`, and user-origin rules are
explicitly allowed to relax ASK.

Memory/Reflex scoping itself holds: a fact added in env `dev` is
invisible in env `other` and present again after switching back
(verified live). The leak is the permission fragment, not the state
stores. No config key can disable audit (there is no audit switch
in config at all), so that half of the claim holds vacuously.

## 6. Sandbox escape — FAIL

Backend on this host is bwrap, filesystem-only (container backend
honestly unavailable; network isolation not in effect — disclosed).
Probes run through the real `BwrapBackend.run`:

| Probe | Result |
|---|---|
| `cat link-out.txt` (symlink → `/tmp/sbx-secret.txt`) | Blocked (`No such file or directory`) |
| `cat /tmp/sbx-secret.txt` (absolute path outside) | Blocked (`No such file or directory`) |
| `cat hard-out.txt` (**hardlink** to the same secret, planted in the workspace) | **READABLE — `SECRET-OUTSIDE`, exit 0** |
| `cat /etc/passwd` | Readable (bound read-only by design; world-readable on host anyway) |
| `cat /proc/1/cmdline` | Readable — exposes the full bwrap argv incl. the host workspace path |
| Write to `/tmp/sbx-escape-write.txt` | Contained (landed in the sandbox's private tmpfs; no host file) |
| Network egress (`urllib` to example.com) | Failed (no route in this sandbox; filesystem-only is disclosed, so no claim is made here) |

The hardlink read is the escape: a file outside the workspace is
readable inside the box through an inode the workspace already
holds. This was a documented known limitation in v0.5.0 (R2-3,
`sandbox.py` module docstring: "a hardlink planted in the workspace
is the same inode under another name") — it persists, and the v0.9.0
selftest sandbox leg does **not** probe it: its "denied read" check
is `cat <absolute path outside the workspace>`, which fails only
because the path does not exist inside the tmpfs root, not because
of any access control. The leg therefore overstates the isolation it
proves. (A container backend does not fix this either — a bind
mount carries the same inode — so the fix is a workspace copy or a
separate filesystem, not a backend swap.)

Secondary observations (not standalone FAILs): `/proc/1/cmdline`
exposes the full bwrap command line including host paths (same
v0.5.0 residue class); the host env var
`JARVIS_DAEMON_EGRESS_APPROVAL_SOCK` is visible inside the sandbox
— the env scrubber is a denylist (KEY/TOKEN/SECRET/… segments) and
this var matches none of them. It is a socket path, not a
credential, but it shows scrubbing is not an allowlist.

## 3. Plan-mode bypass — FAIL (narrowed, but the headline attack still works)

Three of the four sub-findings are genuinely fixed, verified live.
The headline finding 3a is not: the round 1 reproduction still
executes a forged plan end to end, twice in a row with different
content. The fix moved the defence from the file's self-stored
hash to the approval panel, and the panel is the only defence
against a pre-approval forgery — the kernel check never bites on
it, because the approval it compares against is written from the
same forged file seconds earlier.

### What is fixed (verified live)

- **3b — stale REPL tracker.** Under a pty, `/plan add a
  docstring to a.py`, forge the stored plan to `b.py`, `/build`,
  answer `a`: the run's task header reads `task 1: Execute: add a
  docstring to b.py` and the approval panel shows `files b.py` —
  the REPL ran the EDITED plan's task, not the stale `/plan`-time
  tracker. (The file effect is uninformative with the demo
  provider: it keys off the session's first user message and edits
  `a.py` whatever the brief says — the builder disclosed this, and
  the brief/tracker is what a real model acts on.)
- **3c — "always" scoping.** Same REPL session: after the first
  `/build` answered `a`, re-forge the plan to `a.py` and `/build`
  again — the prompt reappears (1 `allow?` prompt on the second
  build). The hash-scoped session key
  (`plan.execute:<id>:<hash[:16]>`) works as claimed.
- **In-window tamper.** The mechanism test
  `test_forged_plan_with_recomputed_hash_refuses` passes: approve
  hash H1, emit the approval, forge the file to H2,
  `verify_approved` refuses with "changed after approval". The
  window protected is the one between the pre-prompt load and the
  post-approval re-load — a real window (the whole approval
  interaction), not a sub-second race.
- **Panel visibility.** The approval panel now shows task titles,
  descriptions, and files (verified in the live transcripts).

### What is NOT fixed — 3a, reproduced live (CLI)

Fresh workspace `/tmp/r2-ws` (`a.py`, `b.py`), isolated
`DAEMON_HOME=/tmp/r2-home`:

```
$ daemon run --plan "add a docstring to a.py" --provider demo -w /tmp/r2-ws
plan 08a1518c created (not executed)
```

Forge as in round 1 (retarget task to `b.py`, recompute the hash
with the public `compute_plan_hash`), then under a pty answer `y`:

```
APPROVAL REQUIRED
  action  Execute plan 08a1518c: add a docstring to a.py (1 task(s), hash c8ebccbd724b)
  files   b.py
  tasks   (approving exactly these tasks)
    1. Execute: add a docstring to b.py — Tampered: operate on b.py instead of a.py.
       files: b.py
...
plan executed: all tasks done
```

**`b.py` was edited; `a.py` untouched.** Then re-forge back to
`a.py` (new hash `47358714de0c`) and execute again with `y`:
**`a.py` was edited too** — the second forged plan also executed.
The kernel's own record proves the anchor exists and is unused:

```
plan.created  | plan_id 08a1518c | hash 5a03d698775c | tasks [('Execute: add a docstring to a.py', ['a.py'])]
plan.approved | plan_id 08a1518c | hash c8ebccbd724b | tasks [('Execute: add a docstring to b.py', ['b.py'])]
plan.approved | plan_id 08a1518c | hash 47358714de0c | tasks [('Execute: add a docstring to a.py', ['a.py'])]
```

`plan.created` holds the original content and hash — and nothing
ever compares against it. `verify_approved` (`daemon/plans.py:291`)
compares the file's fresh hash against the LATEST `plan.approved`
event, but every execute path emits that approval from the
currently loaded record (`daemon/cli.py:646`,
`daemon/cli.py:937`, `daemon/ui/repl.py:436`) BEFORE re-loading
and verifying. So the recorded hash always equals the current
file's hash at verify time, and the check can only fire on a
tamper inside the approval window. The round 1 fix list asked
explicitly for the creation-event comparison ("Record the content
hash (and plan id) in the `plan.created` kernel event and compare
at execute time"); the builder recorded the hash in
`plan.created` but never compares against it, citing the
edit-before-approve flow (the CLI itself prints "Edit the file to
change it, then execute with: daemon run --execute-plan …").

Two things make the panel an insufficient substitute for that
comparison:

1. The panel's most prominent line is the action header, built
   from the plan's `goal` — which the forger controls too. In the
   probe above the header still read "add a docstring to a.py"
   while the task targeted `b.py`; a forger who also rewrites the
   goal makes the panel fully consistent with the forgery. The
   panel shows what the file says, not what the user asked for —
   and the only independent record of what the user asked for is
   the `plan.created` event, which is never shown.
2. The test suite now pins the vulnerable behaviour as intended:
   `test_execute_plan_panel_shows_tampered_tasks` asserts
   "execution follows the approved (tampered) content". A fix
   round will have to change that test, not just the code.

`--yes` still never substitutes for plan approval
(`approve_plan` neutralises assume-yes; a piped-`y` non-tty run
refuses with "plan execution not approved — nothing ran"), so the
attack needs the user at the prompt — but the prompt is exactly
where the forgery is supposed to be caught, and it does not catch
it.

### New surface probed: forging the kernel record itself

Can an attacker write a `plan.approved` event directly into
`events.db` and then execute? **Yes — demonstrated live.** With
write access to `~/.daemon/events.db`, a plain `sqlite3` INSERT
of a `plan.approved` event carrying the forged hash (and a direct
UPDATE of the same table, proving the store is mutable) makes
`verify_approved` pass and the forged plan execute (`b.py`
edited, "plan executed: all tasks done"). There are no SQLite
triggers enforcing append-only; it is module convention only
(`daemon/events.py` — `CREATE TABLE` with `UNIQUE(run_id, seq)`,
no trigger; the only UPDATE/DELETE guard is that no code path
calls them).

This is **not a FAIL** and does not change the 3a verdict: the
threat model is a workspace-confined forger (a model run that can
write `.daemon/plans/*.json` through daemon tools). That forger
cannot reach `DAEMON_HOME` — path containment blocks it, and the
sandbox constrains shell. A process with write access to
`DAEMON_HOME` already runs with the user's full privileges and
could approve the plan itself, so forging the event gains it
nothing. The kernel's trust boundary is `DAEMON_HOME` file
permissions — the same assumption the audit log, grant store,
and session journal already rest on. Recorded here so the
boundary is explicit: if a future design ever needs the event
log to be tamper-evident against a stronger adversary, it needs
triggers or hash-chaining, not convention.

### Fix direction for round 3

At execute time, compare the loaded plan against the
`plan.created` kernel event as well as the approval. When they
differ, show the creation-vs-current diff in the approval panel
— the user then knowingly approves their own edit (preserving
the edit-before-approve flow) while a forger's silent retarget
is surfaced as a change, not hidden behind a panel that merely
repeats the forged file. The alternative (refuse any plan whose
hash differs from creation, requiring re-creation after an edit)

## 3d. REPL recorded edit path (`/edit-plan`) — FAIL

**The REPL half of the recorded edit path does not exist as a
user-facing command.** `/edit-plan` is listed in `/help` and named
in the CLI's own guidance (`verify_approved`'s refusal message:
"re-record the edit with `daemon plan --edit <id>` (or /edit-plan
in the REPL)"), but typing it in the REPL answers:

```
› unknown command /edit-plan (/help)
```

Reproduced live twice — once with piped stdin, once under a real
pty (`script`), in both cases with `/help` in the same session
advertising the command:

```
/edit-plan
               edit the active plan in $EDITOR and record the edit: /edit-plan
```

Root cause (`daemon/ui/repl.py`): `_dispatch` builds the handler
name with no hyphen→underscore conversion —

```python
handler = getattr(self, f"_cmd_{command.lstrip('/')}", None)
```

— so `/edit-plan` looks up `_cmd_edit-plan`, which does not
exist. The method is `_cmd_edit_plan` (`repl.py:389`). It is the
ONLY hyphenated slash command in `SLASH_COMMANDS` (all 28 others
are single words), so it is the only one that can never dispatch;
`_dispatch` is the sole slash-command entry point (`start()` loop,
`repl.py:110-112`). The bug was introduced with the R2 fix itself
(`da8a8a7` is the only commit touching `/edit-plan`) and has never
worked.

Why the suite did not catch it: the test that claims to drive it,
`test_repl_build_executes_edited_plan`
(`tests/unit/test_plan_mode.py:378`), calls `repl._cmd_edit_plan("")`
directly — it exercises the method, never the wiring. The
green test is a false green for the user-facing command: the
build report's claim ("REPL /edit-plan") is unproven at the
level the user touches it.

Security impact of the defect itself: none in the bypass
direction — a dead command cannot re-record a forgery, which is
why the piped-REPL forgery chain I probed (decline demo →
`/edit-plan` with a forge EDITOR → `/build` → `y`) dies at the
`/edit-plan` step. But the legitimate flow is broken with it: a
REPL user whose plan file was rewritten (by hand, or by an agent
run) is told by the error message to use `/edit-plan`, and the
REPL answers "unknown command". The CLI path
(`daemon plan --edit`) still works from a shell, so recovery is
not wholly absent — but the fix's own advertised REPL recovery
path is a dead end, and the test suite asserts the feature works
while it does not. The fix is one line (normalize hyphens in
`_dispatch`, e.g. `command.lstrip('/').replace('-', '_')`) plus a
test that drives the command through `_dispatch`, not the method.
